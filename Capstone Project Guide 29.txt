## 1. Purpose of the Capstone Project

The capstone project is the practical outcome of the course. Your team will build a small but complete generative AI product that solves a clear real-world problem and can be demonstrated through a working application. Public deployment is optional. A working published URL earns +5 bonus points.

The goal is not to build a large commercial system. The goal is to show that your team can connect the main concepts from the course in one useful product:

1. Use a language model through Python with a clear prompt and structured output.
2. Build a RAG pipeline that retrieves useful evidence from a knowledge source.
3. Build an agent that can select and use at least two useful tools.
4. Present the result through a working application that can be run and demonstrated locally or online.
5. Explain the main design choices, limitations, and safety considerations.

You have full freedom to choose the project idea, domain, model provider, embedding model, vector database, agent framework, user interface, and deployment service. The selected technologies may be free or paid. Marks are awarded for correct use of the concepts, not for using an expensive service.

> **Core project flow**  
> User input -> RAG retrieval -> Agent decision -> Tool execution -> Grounded final response -> Working application

## 3. Minimum Practical Requirements

### 3.1 Day 1 Concepts - 10%

Use the Day 1 **model-to-solution** process as a simple planning guide:

```text
Real problem and target user
-> Required inputs and expected output
-> Model and API choice
-> Prompt, context, and structured response
-> Validation and error handling
-> Working application and user experience
```

Review the Day 1 slides for extra guidance, especially the difference between a model and a complete solution, the system layers, and the development lifecycle.

The product should show the basic model-to-application flow:

- The main logic is written in Python.
- The application calls a language model through an API or an approved local model.
- The prompt clearly defines the model's role, task, limits, and expected output.
- The output is organized for the product, such as JSON, a table, a checklist, a report, or clearly defined fields.
- The application handles missing input, unsupported files, model errors, or insufficient evidence in a clear way.
- The team can explain how the prompt was improved after testing.

### 3.2 RAG - 25%

The RAG component should be visible in the code and understandable to the team. At minimum, it should include:

- A useful knowledge source related to the problem.
- Document or data ingestion.
- Text extraction and basic cleaning where needed.
- A reasonable chunking method.
- An embedding model.
- A vector database or vector store.
- Query embedding and retrieval of relevant chunks.
- Metadata such as source name, page, section, category, or record ID.
- A grounded prompt that uses the retrieved evidence.
- Sources shown in the final result when possible.
- A clear response when the knowledge base does not contain enough evidence.

The code should clearly separate the two RAG stages:

**Knowledge preparation:**  
Documents -> Extract -> Clean -> Chunk -> Embed -> Store

**Product runtime:**  
User query -> Query embedding -> Retrieve -> Build context -> Generate grounded answer

### 3.3 Agent and Tools - 25%

The agent should perform a useful decision, not only run a fixed list of functions. At minimum:

- The agent has access to at least **two meaningful Python tools**.
- Each tool has a clear purpose and defined inputs and outputs.
- The agent selects the appropriate tool based on the user request or intermediate result.
- A request may use Tool 1, Tool 2, or both when appropriate.
- Python code validates the tool arguments before execution.
- The result of the tool is returned to the agent or final product pipeline.
- The agent has a stopping condition, step limit, timeout, or another simple control.
- Tool errors are handled without crashing the full application.
- Sensitive or high-impact actions should require confirmation or should be simulated safely.

RAG retrieval does not count as one of the two required tools. The project must show both RAG and at least two additional useful tools.

Examples of meaningful tools include calculating a compliance score, producing a CSV report, creating a study plan, generating a maintenance ticket, ranking suppliers, formatting tasks, checking a date, or searching an approved structured dataset.

## 4. Recommended Product Architecture

A simple architecture is enough. The following structure is recommended because it keeps the course concepts visible:

### Offline knowledge preparation

```text
Knowledge files or records
        |
        v
Extract and clean content
        |
        v
Create coherent chunks and metadata
        |
        v
Generate embeddings
        |
        v
Store vectors in the selected vector database
```

### Online product flow

```text
User uses the working application
        |
        v
Validate the input
        |
        v
Retrieve relevant evidence from the vector database
        |
        v
Send the request, evidence, and available tools to the agent
        |
        v
Agent selects and runs Tool 1, Tool 2, or both
        |
        v
Return a structured answer with sources and useful output
```

A simple Streamlit interface is recommended because the course uses Python. Other interfaces are allowed if the team understands and can explain them.

Teams have freedom to choose their technologies. The following options are suggestions, not mandatory requirements.

| Component | Easy recommended option | Other acceptable options |
|---|---|---|

### Recommended simple path

For the lowest setup complexity, use:

**Python + Streamlit + Gemini + Qdrant Cloud + GitHub**  

For teams that want the optional deployment bonus, Streamlit Community Cloud is the recommended publishing service.

Qdrant Cloud provides a free cluster suitable for prototypes. Supabase is a useful alternative when the project also needs relational tables, file storage, or user data. Gemini currently provides free-tier options for supported models and embeddings. Provider limits may change, so verify the current account limits before the final demo.

### Data options

The project does not require a large dataset. A small, relevant, clean dataset is better than a large random dataset.

Teams may use:

- Public documents or open datasets.
- Sample policies, manuals, procedures, job descriptions, lecture notes, or product specifications.
- Team-created documents.
- Synthetic data generated for the project.
- A small combination of PDF, text, CSV, image, or audio inputs when relevant.

If synthetic or generated data is used, state this clearly in the README. Do not upload confidential, personal, copyrighted, or sensitive information without permission.

## 8. Five Suggested Real-World Project Ideas

These ideas are examples only. Teams have full freedom to select another useful problem as long as all assessment requirements are met.

### Idea 1 - Meeting-to-Action Assistant

**Problem:** Teams lose decisions, responsibilities, and deadlines after meetings.  
**Input:** Meeting transcript plus project guidelines or team information.  
**RAG:** Retrieves project roles, policies, deadlines, and approved task formats.  
**Possible tools:** Extract and normalize dates; export action items to CSV or a formatted report.  
**Output:** Decisions, tasks, owners, deadlines, risks, and a downloadable action plan.

### Idea 2 - Requirements and Document Compliance Checker

**Problem:** Reviewing a proposal against a requirements document is slow and inconsistent.  
**Input:** Requirements document and submitted proposal.  
**RAG:** Retrieves the relevant requirement and supporting evidence from both files.  
**Possible tools:** Calculate a compliance score; export a compliance report.  
**Output:** Compliant, partially compliant, or missing requirements with sources.

### Idea 3 - Smart Lecture Study Assistant

**Problem:** Students need a faster way to study long lecture slides and transcripts.  
**Input:** Lecture slides, transcript, and student question.  
**RAG:** Answers from the approved lecture material with slide or page references.  
**Possible tools:** Generate flashcards; create a study plan or quiz file.  
**Output:** Grounded answers, summary, key concepts, questions, and study resources.

### Idea 4 - Procurement Offer Comparison Assistant

**Problem:** Comparing supplier offers against technical and purchasing rules takes time.  
**Input:** Supplier offers, purchasing requirements, and evaluation criteria.  
**RAG:** Retrieves exact requirements, specifications, and supplier evidence.  
**Possible tools:** Calculate weighted supplier scores; generate a comparison report.  
**Output:** Comparison table, missing requirements, risks, scores, and recommendation.

### Idea 5 - Maintenance Inspection Assistant

**Problem:** A technician needs quick access to relevant procedures during initial inspection.  
**Input:** Equipment description or image, reported symptoms, and maintenance manual.  
**RAG:** Retrieves relevant manual sections and safety instructions.  
**Possible tools:** Calculate a simple risk level; create a maintenance ticket or checklist.  
**Output:** Possible issue, evidence, safety warning, inspection steps, and a structured ticket.

## 11. Ten Questions Your Team Should Be Ready to Answer

1. **What real problem does the product solve, and who is the target user?**  
   Explain the user, pain point, and expected benefit in one clear statement.

2. **Why is a language model useful for this problem?**  
   Identify the task requiring understanding, extraction, classification, generation, or reasoning.

3. **Why did you use RAG instead of sending only a direct prompt?**  
   Explain what private or project-specific evidence the model needs.

4. **What data did you use, and how was it prepared?**  
   Mention extraction, cleaning, chunking, metadata, and any synthetic data.

5. **Which embedding model and vector database did you choose, and why?**  
   Give a practical reason such as cost, simplicity, language support, or deployment needs.

6. **How does the agent decide which tool to use?**  
   Explain the available tools, tool descriptions, and decision flow.

7. **Show one request that uses Tool 1 and another that uses Tool 2.**  
   Be ready to demonstrate that the tools are selected based on the task.

8. **What happens when the required information is not in the knowledge base?**  
   Show that the product does not confidently invent unsupported information.

9. **How did you test the product and handle errors?**  
   Mention normal cases, missing data, failed retrieval, invalid input, and tool failure.

10. **What is the main limitation, and what would you improve next?**  
    Give an honest and realistic improvement rather than claiming the product is perfect.
